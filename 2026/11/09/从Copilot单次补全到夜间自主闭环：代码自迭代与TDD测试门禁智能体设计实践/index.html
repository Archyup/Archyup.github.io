从 Copilot 单次补全到夜间自主接力：基于 TDD 测试门禁的代码自迭代智能体原型实践

发表于 2026-11-09 更新于 2026-11-13 分类于 技术实践

大一刚入学参加岳麓黑客松时，我还只写过两个月代码，连调外部 API 都要跟着学长一步步摸索；当时我在随笔里写过一句偏感想的话，觉得做应用只要学会把现成 AI 能力串起来就行。

转到大二上学期，这段时间刚打完先导杯（海光 DCU 上的算子与推理优化），这两天又在看 世界计算大会 × 昆仑元 × AMD 黑客松 的赛题规则。

赛制里有个让我特别在意的环节叫 “碳硅接力 / 夜间自主研发”：白天由选手写清楚接口骨架和测试用例，夜间人离场，交给脚本里的 Agent 自己跑编译与单测、读取报错再改代码，第二天早上看结果。

yysy，平时用 Copilot 或 Cursor 补全时，我们其实很少意识到自己充当了多少“人肉胶水”：模型给一段代码，人手动点 Accept、跑测试、把 Traceback 贴回对话框、再让它改。一旦真的让人退场过夜，最大的问题通常不是模型不会写某一行语法，而是没有强约束时很容易出现两种翻车：要么死循环空转，要么模型为了“让单测通过”干脆把测试文件里的断言改掉。

为了先把这套思路跑通，我这几天写了一个叫 ACS-Agent（Autonomous Code Synthesis & Verification Agent） 的实验性脚手架。先说明边界：目前它还是一个验证控制流与 TDD 闭环机制的轻量原型，在真实 LLM 泛化评估、系统级安全沙箱和严格数值测试上都还有明显的待完善项。这篇笔记就把代码架构、演示机制以及这次代码审查后暴露出的问题和工程边界一起摊开记录清楚。

一、 问题拆解：为什么夜间自主迭代不能只是“多轮对话”

把代码生成从单次交互拉长成无人值守的循环，本质上是把原本由人类做的三件事接管下来：运行门禁、截取有限上下文的报错、限制允许改动的文件范围。

维度 常见补全工具 对话框多轮调试 带 TDD 门禁的脚本闭环
驱动模式 光标处被动预测下一行 依赖人复制报错与发起下一轮 由 unittest 失败状态触发下一轮迭代
上下文来源 附近代码窗口 人手动粘贴整段终端日志 扫描并截取关键报错行，避免撑爆上下文
防作弊边界 人肉审代码 人肉阻止改测试 调度层限定可写路径，不向测试文件开放写接口
当前定位 成熟日常助手 成熟交互方式 探索夜间循环的自动化脚本原型

整个系统的主循环可以画成下面这条控制流：



flowchart TD
    S["读取目标源码与 TDD 测试说明"] --> G["调用 LLM 后端生成完整目标源码"]
    G --> AST{"AST 语法预检"}
    AST -- "SyntaxError" --> F1["拒绝落盘 (SYNTAX_ERROR)，保留磁盘旧代码"]
    F1 --> LIMIT{"超过 max_iterations?"}
    AST -- "通过" --> W["写入 target_file（测试文件不在写接口作用域）"]
    W --> T{"执行 unittest 子进程（15s 超时）"}
    T -- "returncode == 0" --> OK["退出循环并输出 diff 记录"]
    T -- "FAIL / ERROR / Timeout" --> E["按关键字提取 Traceback 喂给下一轮"]
    E --> LIMIT
    LIMIT -- "否" --> G
    LIMIT -- "是" --> FAIL["终止并保留过程历史"]

二、 现有核心模块：到底做了什么，没做什么

按真实代码结构看，这个项目主要拆成工具层（src/tools.py）、LLM 后端适配层（src/llm_backend.py）、提示词组装（src/prompts.py）和 ReAct 状态机主循环（src/agent.py）。

2.1 ToolBox 的约束设计，以及目前离“真沙箱”的差距

在原型设计里，我希望保证 Agent 只改被测的实现文件，不碰门禁测试文件，同时别把明显残缺的代码写进工作区，也不能让死循环脚本把宿主机一直卡死。

在 src/tools.py 里实际落地了三个基础动作：

  1. 文件读写与路径限定：CodeIterationAgent.execute_step 在代码逻辑上只把 self.target_file 传给 ToolBox.write_source，因此在这个固定 ReAct 循环里，模型输出的代码只会写到目标实现文件，不会覆盖 test_file。write_source 内部就是普通的 open(..., "w") 工作区文件覆写，还没有做临时文件落盘再 os.replace 的原子替换。
  2. 报错行提取：测试失败时，run_tdd_gate 会按行扫描标准输出与错误流，遇到包含 "FAIL:"、"ERROR:" 或 "Traceback" 的行时打开捕获开关并将后续输出收集起来作为 traceback 片段（若未命中则回退为整段剥除首尾空白的原始输出 raw_output.strip()），而不是依赖复杂正则解析调用帧。
  3. 关于“沙箱”的真实水位（重要边界）：run_tdd_gate 目前底层只是调用标准库 subprocess.run(..., timeout=timeout) 在当前 Python 环境中跑 unittest（[sys.executable, "-m", "unittest", abs_test_path]），默认超时 15 秒。也就是说，现阶段代码里并没有文件系统权限隔离（比如 chmod 只读锁）、路径穿越校验（_resolve_path 未拦截 .. 逃逸）、网络隔离或容器/chroot 进程隔离。它依赖的是调度层不乱传路径的“应用层约定”；如果直接挂接一个拥有自由 Bash 权限的模型或跑在不可信代码仓库里，这样的隔离力度显然是不够的。

2.2 状态机主循环与 AST 拦截

src/agent.py 里的 CodeIterationAgent 把每轮执行结果记录在 self.history 列表里，单轮 execute_step 的节奏很直接：

  • 门禁驱动：先跑一遍 run_tdd_gate(self.test_file)；如果返回 passed == True，立即以 CONVERGED_SUCCESS 状态结束；如果失败，再读取当前磁盘上的 target_file 源码和 traceback（或 output）调用 build_error_feedback_prompt 构造下一轮提示词。
  • 生成与语法预检：通过 self.llm.generate_patch(...) 返回 (thought, patched_code) 后，先调用 validate_syntax 做 ast.parse。如果不合法，直接返回 SYNTAX_ERROR 状态拒绝写盘，防止坏补丁把当前工作区搞坏；合法才会计算 unified diff（compute_diff）并调用 write_source 覆盖目标文件。从目前实现上看，被 AST 拦下的那轮报错还只是记录在 step_log 供前端/日志查看，并没有拼进下一轮 prompt，这点也留待后续顺手补齐。
  • 可观测性：run_demo.py 在终端打印每一轮的 diff 行数与状态，仓库中也附带了 run_web.py 供 Streamlit 面板回放每一步的 step_log。

2.3 双后端：LiveLLMClient 与离线 DeterministicMockLLM

为了让项目在没有 API Key 时也能直接运行整套流程、tests/ 和前端界面，src/llm_backend.py 设计了一个抽象基类 BaseLLMBackend 和两套具体实现：

  • LiveLLMClient（真实推理后端）：调用 OpenAI 兼容的 /chat/completions 接口（适配 OpenAI、DeepSeek、阿里百炼 DashScope 或本地 vLLM/Ollama；若接入非 OpenAI 协议模型需经过兼容代理），输出 thought 与补丁代码。
  • DeterministicMockLLM（离线确定性模拟引擎）：这里需要非常坦诚地说明它的真实机理。DeterministicMockLLM 不是一个在未知问题上动态推理的本地小模型，而是通过关键词匹配上下文中的 "spmm"、"vector"、"kv" 字符串，命中后返回预先写好的修复代码与预设 Thought 模板。

注意区分“流程演示通过”和“模型真会修 Bug”：在离线 Mock 模式下看到 100% 收敛，只代表 Agent 主循环调度、Traceback 回传、AST 预检、覆写和单测状态刷新这条控制流代码没有写错；它绝不能当成真实大语言模型能够独立解决未知工程 Bug 的能力证明。

三、 闭环流程演示与精度自查

仓库里的 run_demo.py 自带三个小用例（benchmarks/case1_spmm_boundary、case2_vector_scale、case3_kv_cache_broadcast），再加上 tests/ 目录下的 4 个单元测试，用来在无外网环境下回归控制流。

老实说，回头逐行复核代码时，我发现演示用例里之前有一处描述严重超前于实际代码的问题，必须在这里直接改口纠偏：

  1. Case 1（SpMM CSR 边界处理演示）：benchmarks/case1_spmm_boundary/kernel.py 默认漏了空行保护和列边界检查，test_kernel.py 测了常规 CSR 矩阵、空行 NNZ=0 以及正方向列越界 col_indices=[0, 999]（需要说明：test_kernel.py 并没有测负列索引测试用例，早期文案提的负索引门禁在测试里其实没写）。Mock 补丁补上空行早退和有效列界判断后测试通过。
  2. Case 2（Vector Scale 与数值表述纠偏）：原先演示脚本横幅里写了 0-ULP Float Precision 的标题，实际打开 benchmarks/case2_vector_scale/test_kernel.py 和 Mock 代码一看，测试数据仅仅是 [1.0, 2.0]、[3.0, 4.0] 配 scale=2.5 对照 [10.0, 15.0]，且 Mock 实现只是顺手在 Python float64 里写了 round(..., 6)。保留六位小数跟 IEEE 754 float32 逐位一致（0-ULP）完全是两码事：既没有测 IEEE-754 单精度舍入行为，也没有覆盖极小/极大数或正负相消。把这套 round(..., 6) 的玩具测试说成“0-ULP 精度对齐”属于典型的术语滥用，这篇文章里正式收回，只将其视为最基本的标量乘法参数漏传修复演示。
  3. Case 3（GQA KV Cache 广播展开）：用 Python 列表和切片构造测试数据，验证 2 头 KV Cache 按分组比例（G = 12 / 2 = 6）做 repeat-interleave 扩展对齐到 12 头 Query 的逻辑能够收敛通过。

在实际终端运行 python3 run_demo.py（离线 DeterministicMockLLM 模式）与 python3 -m unittest discover -s tests -v 的观察如下：

  • tests/ 下的 4 项框架自身单测（TestAgentLoop.test_vector_scale_case_convergence 以及 TestToolBox 对读写、语法检查和 Diff 的测试）用时 0.122s，全部 OK。
  • run_demo.py 在离线 Mock 模式下 3 个演示用例都在第 2 轮完成测试转绿，总壁钟时间约 0.38s（Case 1 约 0.15s、Case 2 约 0.099s、Case 3 约 0.127s）。同样再强调一遍：这个结果验证的是脚本闭环跑通，不代表真实 LLM 的修复能力。

四、 已知限制与后续待完善边界

既然定位是一个先跑通主逻辑的黑客松前期原型，把短板列出来比写漂亮口号更有意义：

  1. 真实 LLM 端到端评估缺失：目前公开的仓库记录跑通的是 DeterministicMockLLM；真实使用 LiveLLMClient 时，针对长仓库跨文件依赖、模型改代码越改越散、Token 成本与真实收敛率，还需要建一套不靠关键词命中、有真实随机/陌生 Bug 的评测集去实测。
  2. 安全隔离仅停留在应用层约定：ToolBox 目前没有操作系统级别的测试文件只读锁、工作目录越界路径校验（_resolve_path 应加入 .resolve() 后缀前缀检查拦截 ..）、以及轻量容器隔离，因此暂时不适合直接运行不可信代码或开放 Shell 工具权限。
  3. 单文件全量覆写与数值验证深度不足：现在每次修复是全文件覆写，文件上千行之后成本高也容易改丢上下文；Case 2 若真想服务底层算子开发，需要换成按 struct 解包 FP16/FP32 二进制并统计 max-ULP 的专项检测，而不是 round(..., 6)。

写完这套雏形最大的感受是：把“报错 → 改代码 → 重跑验证”写成一个自动死循环并不难，真正决定这种工具能不能托付整晚的，反而是权限边界是否写死、验证集够不够硬、以及测试通过时到底有没有偷偷放水。后面有空也会优先把 ToolBox 的路径边界和真实模型基准评测补上。
