从 Copilot 单次补全到夜间自主接力：基于 TDD 门禁与双层沙箱的代码自迭代智能体实践

发表于 2026-11-09 更新于 2026-11-18 分类于 技术实践

大一刚入学参加岳麓黑客松时，我还只写过两个月代码，连调外部 API 都得跟着学长一步步摸索；当时我在随笔里写过一句偏感想的话，觉得做应用只要学会把现成 AI 能力串起来就行。

转到大二上学期，刚在先导杯里啃完海光 DCU 上的算子与推理优化，这几天又在全力备战 世界计算大会 × 昆仑元 × AMD 黑客松。这次赛制里最戳我的环节是 “24h 碳硅接力 / 夜间自主研发”——白天由人类定义任务拓扑、接口骨架与测试契约，夜间选手全部撤场，让 Agent 在本地算力或网关节点（如昆仑 GPT-Factory One / AI Agent Gateway、AMD Ryzen AI MAX+ 395 本地推理等）上无人值守自主编码、编译自测、纠错回滚、断点续跑，第二天早上人类直接拿交接报告与补丁包接续推进。

yysy，平时用 Copilot 或 Cursor 写代码时，我们很容易低估自己充当了多少“人肉胶水”：模型给一段补全，人手动点 Accept、切终端跑单测、把 Traceback 贴回对话框再改。真到夜间撤场跑自主循环时，没有强约束马上会翻车：要么死循环把 Token 烧干，要么模型为了“让单测通过”直接去改测试断言；而更隐蔽的翻车点，则是我 11 月 9 日写第一版原型后回头审代码时暴露出来的那一堆工程欠账——没有路径逃逸校验、测试跑在原工作区缺乏容器隔离、不支持 C++/HIP 编译门禁、长程 ReAct 上下文爆窗、以及缺乏零泄漏未知题评测。

经过两轮深度迭代，我把这套 ACS-Agent（Autonomous Code Synthesis & Verification Agent） 推进到了完全体，开源在 GitHub：https://github.com/aarchyyy/autonomous-code-agent。整个核心引擎、评测框架与实时 Web 工作台完全基于 Python 3.9+ 标准库（零第三方强制依赖），打通了 双层执行沙箱（进程 rlimit + Rootless 无网只读 Docker 容器）、Python AST 细粒度白名单 + C++17/HIP 原生编译预检、多文件 ReAct + 上下文滑窗保配对压缩、全模式 STALLED 熔断、24h Kahn DAG 拓扑接力与断点重验续跑，以及 8 项安全红队 + 4 道跨语言未知题泛化压测。目前 34 项单元、容器隔离与红队对抗测试 100% 通过（32.189s），这篇把完整架构演进、核心代码机制与实测证据链一次摊开讲透。

二、 双层隔离沙箱与多语言预检：src/sandbox.py

要让 Agent 在夜间自由修改 Python 与 C++/HIP 代码而不污染工作区或泄漏密钥，所有底层防线统一收敛在 src/sandbox.py 中。

2.1 PathGuard 与 IntegrityMonitor：零信任路径与双次 SHA-256 核验

  1. 物理路径规范化与软链逃逸拦截：PathGuard.canonicalize 将所有相对或绝对路径统一经 os.path.realpath 展开（即便目标文件尚未创建，指向工作区外的父目录软链同样会被解析），强制验证 os.path.commonpath([self.workspace_root, real_candidate]) == self.workspace_root。
  2. 严格读写 ACL 与隐藏集物理隔离：封禁 .git 与 .acs_runs 访问；hidden_files（隐藏 Holdout 测试）在 read_file、list_files、search_code 中彻底隐身，且在常规 TDD 阶段根本不会被拷贝进临时执行目录；check_write 仅放行 writable_files 白名单。
  3. 测试前后双次哈希核验：IntegrityMonitor 在门禁执行前、后各核对一次所有受保护测试与 Holdout 文件的 SHA-256 摘要，任何篡改立即抛出 IntegrityViolationError 并回滚。

2.2 Tier 1（进程级 rlimit）与 Tier 2（Rootless 无网只读 Docker 容器）

IsolatedTestRunner 支持通过 --sandbox process|docker|auto 在两套物理隔离层级间无缝切换：

  • Tier 1 进程级隔离沙箱（默认零外部依赖）：在 tempfile.TemporaryDirectory 临时拷贝中将受保护文件设为 0o444 只读；_sanitized_subprocess_env() 自动剥离所有名称含 KEY、TOKEN、SECRET、PASS、AUTH 等敏感字段的环境变量；以 python -I 隔离模式配合 start_new_session=True 启动子进程，内部施加 RLIMIT_CPU、RLIMIT_FSIZE（Linux 下含 RLIMIT_AS），超时直接 os.killpg(..., SIGKILL) 清空整个进程组。
  • Tier 2 Rootless 无网只读容器沙箱（--sandbox docker）：针对不可信代码提供内核级隔离——禁用全部网络（--network none）、根文件系统只读（--read-only）、工作区只读挂载（-v <stage>:/workspace:ro）、剥离全部 Linux Capabilities（--cap-drop ALL）、禁止提权（--security-opt no-new-privileges）、以 65534:65534（nobody）身份运行并限制 --pids-limit 64 与内存/CPU 配额；超时除杀死客户端进程组外还会强制执行 docker rm -f 杜绝孤儿容器残留：

2.3 细粒度 AST 白名单与 C++17/HIP 编译器前端预检

早期版本启用 strict_ast=True 时会把 ctypes、json、pathlib 等合法工程依赖一并封死，且无法校验 C++/HIP 算子代码。完全体做了两项关键升级：

  1. 细粒度静态白名单：ASTPolicyInspector.inspect(code, strict=True, allowed_imports=..., allowed_calls=...) 支持在封锁 subprocess、socket、os、eval、exec 的同时，按任务粒度精准放行白名单模块（可通过 CLI --allow-import 或 relay_plan.json 配置）。
  2. C/C++/HIP 落盘前语法与类型预检（NativeSyntaxInspector）：当目标文件为 .c/.cpp/.h/.hpp/.hip 时，落盘前自动在隔离临时目录运行 clang++/g++/hipcc -std=c++17 -fsyntax-only（头文件自动附加 -x c++-header）。模型若漏写分号或写错模板类型，补丁会在触碰磁盘前直接被拦截并把编译器行号诊断回传给下一轮。

三、 多文件 ReAct、上下文滑窗压缩与全模式防退化闭环

3.1 容错型受控工具链与双协议自动降级（src/tools.py & src/llm_backend.py）

ToolBox 向 ReAct 循环暴露 6 个受控工具：list_files、read_file、search_code、patch_file、write_file、run_tests（无自由 Bash 暴露）。针对大模型调 patch_file 时经常因行尾多余空格导致精确子串匹配失败的痛点，_replace_with_whitespace_fallback 增加了行尾空白归一化（rstrip()）唯一连续块回退匹配，并在原子替换（.acs_tmp_<pid> + os.replace）前强制执行 Python AST 或 C++17 语法预检。

在推理端，LiveLLMClient 优先走原生 OpenAI tools 协议；一旦本地轻量网关对 tools 字段返回 HTTP 400，立即无缝降级至文本 [TOOL_CALL] {...} [/TOOL_CALL] 协议，同时兼容提取 <think>...</think> 思考链与 python/cpp/hip 多语言代码块。

3.2 确定性上下文滑窗压缩（src/context.py）与全模式 STALLED 熔断

在多文件仓库里连续执行十几步工具调用后，历史 read_file 和 run_tests 输出很容易撑爆本地模型上下文窗口。src/context.py 新增了 ContextWindowManager：

  • 严格保护协议不变量：永远保留 messages[0]（系统提示词）、messages[1]（任务简报与初始报错）以及最近 keep_recent_messages 条完整消息，且裁剪边界计算时绝不拆散 assistant(tool_calls) 与紧随其后的 role="tool" 响应对（避免触发 OpenAI 接口 400 校验错误）；
  • 结构化折叠历史大观测：对滑出近期窗口的大体积历史工具返回，自动提炼为保留文件路径、行号范围、Diff 行数或错误签名的紧凑 JSON 摘要，并在遥测中精确统计 context_compactions 与 tokens_reclaimed。
  • Patch + ReAct 全模式防退化与防停滞：FileSnapshotManager 追踪最高分状态 (passed_flag, passed_count, -failed_count)，一旦新补丁导致通过数倒退立即自动回滚；同时 _run_patch_loop 与 _run_react_loop 现已全面对齐停滞检测——无论是连续 3 轮门禁落在相同 (state_hash, error_signature)，还是 ReAct 连续 4 次重复完全相同的无效工具调用，都会提前以 status="STALLED" 熔断止损。

四、 24h「碳硅接力」DAG 编排器、断点续跑与实时流式工作台

如果说单任务 Agent 解决的是“怎么把一个模块修绿”，那么面向 24 小时赛制的 src/relay.py 解决的就是夜间十几个工程任务存在先后依赖、共享底层文件、甚至中途断电重启时，如何保证整晚研发队列既不雪崩也不丢进度。

4.1 Kahn 拓扑依赖调度与独立分支故障隔离（RelayPlan.validate_dag）

真实工程任务往往不是一条单链，而是一张有向无环图（DAG）。例如在内置的 benchmarks/night_relay_plan.json 中，T4_multi_file_scheduler 依赖 T1_spmm_csr 与 T2_vector_f32 的数值规范，原生 C++17 算子任务 T5_cpp_csr_spmv 依赖 T1_spmm_csr，而 T3_gqa_kv 则是完全独立的注意力缓存分支。

RelayPlan.validate_dag() 在队列启动瞬间先跑一遍基于入度表的 Kahn 拓扑排序：

  1. 静态拦截重复 task_id、未知前置依赖与循环依赖环路（Cycle detected in RelayPlan）；
  2. 运行期实现精准分支故障隔离：若某个上游根节点（如 T1）未能收敛，依赖它的下游节点会被立即标记为 SKIPPED_DEPENDENCY（消耗 0 次 LLM 调用），而不依赖它的平行分支（如 T2、T3）不受牵连继续正常推进；
  3. 每当一个节点通过自身可见门禁与隐藏 Holdout 后，编排器立刻调用 _run_regression_gates(completed_tasks) 重跑此前所有已收敛节点的门禁。一旦发现后置任务改坏了前置共享模块，当场恢复该任务的 pre_task 快照并打回为 REGRESSION_ROLLED_BACK。

4.2 崩溃安全断点续跑（--resume）与三维预算熔断

跑通宵任务最现实的工程风险之一是进程意外中断（如凌晨机器重启、网关闪断或首轮 Token 预算触顶）。如果在续跑时盲目相信旧日志里的 "success": true，万一工作区文件在中断期间被改动过，就会把坏状态带进后续任务。

因此 RelayOrchestrator 实现了零信任重验式断点续跑（_verify_resumed_task）：

传入 --resume <prior_run_dir> 后，已收敛且重验全绿的任务会以 0 次 LLM 调用直接标为 RESUMED_VERIFIED，同时自动加入 completed_tasks 继续充当后续任务的回归守卫；未完成或重验不通过的任务则无缝重入修复循环。配合三维全局护栏——墙钟时间上限 max_total_seconds（SKIPPED_BUDGET）、Token 总量上限 max_total_tokens（SKIPPED_TOKEN_BUDGET）与连续失败熔断阈值 max_consecutive_failures（SKIPPED_CIRCUIT_BREAKER），彻底杜绝夜间失控账单。

4.3 晨间四件套交付与零依赖 SSE 双模工作台（run_web.py + web/index.html）

为了方便第二天早上人类工程师在 5 分钟内完成审查与合入，夜间接力结束时会自动落盘四份交付物：

  1. HANDOVER_REPORT.md：人类可读的晨间交接简报（含运行模式声明、DAG 依赖表、各任务轮次、SHA-256 完整性、Holdout/回归列与需人工介入条目）；
  2. night_relay_changes.patch：由 FileSnapshotManager.export_unified_patch 汇总生成的标准 Unified Diff 补丁包，即使未开启 --git-branch 也能直接用 git apply 一键合入；
  3. handover_summary.json：供自动化流水线或 --resume 读取的结构化状态快照；
  4. audit_events.jsonl：带 UTC 时间戳与响应 SHA-256 的只追加（Append-Only）事件审计账本。

配套的 run_web.py 与 web/index.html 同样升级到了完全体：基于 Python 标准库 ThreadingHTTPServer + SSE 实时事件流，顶部实时探测宿主机 Docker 守护进程就绪态 与 本地 C++ 编译器（clang++/g++），支持在网页端自由切换 Process / Docker 沙箱、运行 Case 1–5（含 C++17 编译门禁）、填入 --resume 目录断点续跑、监控上下文滑窗压缩次数，并在接力完成后一键下载 HANDOVER_REPORT.md 与 night_relay_changes.patch。

五、 多语言基准集、Docker 实机隔离与零泄漏红队评测（Proof of Work）

5.1 五大内置基准实测（Python 算子 + 原生 C++17 编译门禁 + Rootless Docker）

完全体将内置冒烟基准扩展为 5 个覆盖单文件数值修复、多文件 ReAct 调度与原生 C++17 编译门禁的工程算例：

六、 完全体工程复盘：当人类退场过夜，真正托底的是什么

把 ACS-Agent 从最初几百行的脚本一路打磨到如今支持双层容器沙箱、Python/C++17 双引擎门禁、Kahn DAG 断点续跑与红队评测的完全体，回头看这十来天的踩坑与重构，有四条最深切的工程体会值得沉淀下来：

6.1 四条从实战里踩出来的 Agent 系统铁律

  1. 门禁不仅要“权限只读”，更要“前后双哈希 + 隐藏集防背题”：只限制写工具路径远远不够，必须配合临时隔离目录、环境变量密钥清洗、每次测试前后的 SHA-256 完整性核验，以及对 Agent 完全不可见的 hidden_files Holdout 验收，才能既防“删断言作弊”，又防“硬编码背题过拟合”。
  2. 所有外部依赖层都必须设计优雅降级（Graceful Degradation）：黑客松现场和边缘算力环境充满不确定性——本地网关可能不支持原生 tools 字段（自动降级文本 [TOOL_CALL]）、宿主机未必装了第三方包（全标准库零依赖 + pytest 自动回退 unittest）、有的机器没起 Docker（--sandbox auto 自动在无网只读容器与进程 rlimit 间平滑切换）。不把单点假设写死，系统才真正有生命力。
  3. 长程无人值守的核心不是“永不犯错”，而是“状态可逆与精准止损”：大模型在凌晨写出退化补丁、语法错行甚至死循环是常态。依靠 FileSnapshotManager 最佳分数回滚、os.killpg / 容器强杀看门狗、ContextWindowManager 滑窗压缩、全模式 STALLED 熔断以及 --resume 零信任重验续跑，才能确保任何单轮幻觉都不会污染已收敛的工程资产。
  4. 测试集本身必须先通过“反作弊压力测试”：就像我们在 test_benchmarks_rigor.py 和 RT8 里做的那样——写完门禁后，一定要亲手拿 round(..., 6)、朴素 float32 累加器和离线 Mock 去反向攻击自己的评测集。只有确认投机补丁必挂、离线模拟器在未知题上拿 0 分，测试通过率才真正具备含金量。

6.2 赛场接入 Checklist 与客观运行说明

在实际将完全体投入 24h 碳硅接力运行前，只需按以下三步完成碳基交接准备：

  • 白天定契约：在 relay_plan.json 中梳理清楚模块的 depends_on 拓扑关系，为关键数值/边界条件准备一份不向 Agent 公开的 holdout_test_*，并视需要配置 max_total_seconds 与 max_total_tokens；
  • 选定隔离档位：纯算法或本地可信仓库可直接用默认 --sandbox process 获得毫秒级门禁反馈；若涉及高风险代码执行，开启 --sandbox docker（若容器内需运行 C++/HIP 编译门禁，准备包含 clang++/g++/hipcc 的镜像即可，默认 python:3.12-alpine 面向轻量 Python 门禁）；
  • 夜间跑接力、清晨审补丁：先用 run_demo.py --probe 确认现场网关模型连通性，随后通过 run_relay.py --mode live --git-branch（或打开 run_web.py 实时大屏）启动夜间队列；次日清晨直接对照 HANDOVER_REPORT.md 与 night_relay_changes.patch 快速验收合入。
