深入海光 DCU 异构计算：动态稀疏矩阵乘 (SpMM) 的 Wave64 标量化与长尾负载均衡调优

发表于 2026-11-09 更新于 2026-11-13 分类于 技术实践

接上一篇 Qwen2.5-1.5B 推理底座的总结，这篇复盘先导杯（CSCC）第二道赛题——动态 CSR 稀疏矩阵乘稠密矩阵（SpMM, C = A × B） 与扩展掩码融合算子 ns_spmm_fused_mask 的 HIP 内核调优过程。

yysy，以前学计算机组成原理和体系结构时，总觉得什么寄存器标量化、内存合并、非对称负载偏斜这些概念很抽象，考完试基本就还给课本了。真蹲在海光 DCU 上一行行扒 SpMM 内核才切身体会到，稀疏算子的核心难点往往不在“数学公式多复杂”，而在你必须同时和动态图拓扑、指针非对齐、长尾长行拖垮整个 CU 以及浮点正负相消误差博弈。AI 帮我快速搭起多套 Kernel 变体确实省事，但到最后版本融合、删掉负优化和清查测试假账时，还是得老老实实盯着实机剖析数据和门禁日志说话。

有必要在开头先把这次 /delivery-audit 自查纠偏交代清楚：11 月 9 日初稿沿用了早期 1107 版本的混合数据，里面存在多处未经最终源码/日志对账的表述（例如未对当前二进制反汇编验证的 “24 VGPR / 100% 满占用”、把测试组拼接写错成 “370/370 全过”、以及早期文档行求和笔误导致的 Z200 基线“10.367 ms”）。本文已全部收回这些存疑口径，所有代码分析与实测结果均严格锚定 11 月 12 日整合归档的 Round 12 融合版（solution_template.hip，SHA256 前缀 724010a9） 在 BW（gfx936） 实机上的验证证据。

一、 稀疏算子的真实瓶颈与硬件特征

在动态神经网络场景里，左矩阵 $A$（$M \times K$，CSR 格式）的非零元分布并不是静态写死的，每一帧都可能发生变化（比如重行位置迁移、稠密块漂移或列宽未按 4 字节向量边界对齐）。这会同时诱发三类典型瓶颈：

  1. 间接访存与非对称倾斜（Long-Tail Skew）：CSR 格式需要两跳读取（先读 ci[p] 拿列号，再算出 B[ci[p] * N + j] 的偏移）。更致命的是，像 longtail 这样前几行拥有上千个非零元、其余行只有几个非零元的矩阵，如果只用简单的“1 Wavefront 管 1 行”，少数重行会把单个 Wave 死死拖住，同批短行 Wave 早就算完退出却等不到下一步调度或阻塞整块资源，导致 GPU 利用率骤降。
  2. Wave64 下的地址冗余开销：在 AMD GCN/CDNA 架构的 Wave64 模式下，同一个 64 线程的波前共享同一个行索引 row 和同一套 row_ptr 边界，但编译器如果不作引导，容易将本可全波共享的块/波索引放进每个线程独立的矢量寄存器（VGPR）里参与指针算术。
  3. 精度与兼容性的暗礁：N 未必总是 4 的倍数，B/C 指针未必 16 字节对齐；更隐蔽的是，如果在某些既有极小正数又有超大相消项的输入上随意打破原序改用激进切分累加，可能导致特定列的舍入误差超出容限；而 ns_spmm_fused_mask 在 K == 0 等边界退化情形下如果直接早退不做内存置零，就会留下脏缓冲区导致测试失败。

二、 Round 12 融合版分发路由与核心内核拆解

针对不同矩阵形状与对齐属性，最终交付版 solution_template.hip 在宿主入口 ns_spmm 与 ns_spmm_fused_mask 中采用显式的规则分发，整个路线如下：

    AL -- "是" --> ROUTE{"输出宽度 N 与行数 M 分档路由"}

    ROUTE -- "其余对齐小宽或回退 (N ＜ 128)" --> FB1["csr_vector4_tile / csr_dual4_p1"]

2.1 Wave64 标量提权（__builtin_amdgcn_readfirstlane）与向量访存

在 csr_wave64_scalar_vector4 和 csr_wave64_scalar_dual4_full 等主力内核里，一个 2D Thread Block 固定设为 (64, 4)——threadIdx.x 负责沿输出宽度 N 方向连续迈步（每人借 float4 一次吞 4 个 float），而 threadIdx.y 代表 4 个各自领行任务的 Wave64。

为了让编译器把全波统一的 CTA 行组基准和 Wave 号真正放到标量寄存器（SGPR）并走标量单元算偏移，内核显式使用内置原语做标量提权：

在写入结果矩阵 $C$ 时，由于 SpMM 写出的输出位置一次性写完且后续不再于当前内核内重复读取，对齐快路径通过 store_nt 封装 __builtin_nontemporal_store 提示流式写回绕过缓存分配（需要说明：本次 11 月 12 日并未对当前融合版本单独做关闭 store_nt 的消融测量，故不对“它单独贡献了几成加速比”作无据归因，只保留其作为流式写出机制的设计事实）。

2.2 长尾杀手：use_strided 在线感知与 CTA 4-Wave 协作拆行

早期 38235757 版本虽然微算子带宽已经很快，但在 longtail_1024x1024x256_d5 这类重度偏斜稀疏图上中位耗时仍在 0.0805 ms 左右徘徊，是 6 个公开用例里最明显的提升点。Round 12 针对这个问题在主干内核内加入了两段互补机制：

  1. 轻量行分布启发式 (use_strided)：当 M >= 64 时，在寄存器里只读 rp[0..2] 和 rp[M] 做 $O(1)$ 判定：如果第 0 行的非零元个数 deg0 >= 256，且满足 deg0 * M >= 4 * total_nnz（单行密度至少是全矩阵均值的 4 倍），并且前两行不是共享完全相同起始列的稠密块（!head_block），则打开 use_strided = true。开启后行映射重排为跨步交织（wy * (M/4) + cta_x），把聚集在前排的高负载行打散到不同执行组。
  2. 4-Wave CTA 内协同拆行点积：在 csr_wave64_scalar_vector4 中，当满足 use_strided && (N % 256 == 0) 时，直接切换进协分分支：
    • 每个 wy 先把自己对应的常规短行（nnz < 256）用局部累加器就地算完写出；
    • 遇到长度 $\ge 256$ 的重行，同 CTA 的 4 个 Wave 按 wy = 0..3 把非零元区间 [begin, end) 均切成 4 段各自并行点积（此处内部用 double 做局部 3 路展开点积），各自将结果写到 __shared__ double parts[4][64][4]，再在一次 __syncthreads() 后由 wy == 0 汇总转回 float4 写出。

启发式判据的边界：use_strided 属于 $O(1)$ 零全局扫描开销的头部快速检测，依赖的是典型长尾基准“第 0 行为代表性超重行”这一结构先验；如果某张图前两行极短，而重行出现在中间行段，该启发式不会触发跨步分支——针对移动位置重行的兜底，由宽表非对齐回退路径以及更稳健的动态调度共同承担，而 verify.sh 也专门覆盖了 27 组重行位置动态迁移用例（R0/R32/R64/R127）来检验全位置正确性。

2.3 块稀疏双行寄存器合并（near）与循环展开族

面对 block_1024x1024x256_d25 这类带有连续列块结构（相邻两行共享相同列下标模式）的矩阵，逐行独立读 B 会白白浪费一倍的稀疏行加载流量：

  • 编译期零假设动态 probe：当 !use_strided 且两行构成的一对偶数行边界满足相同度数（$\ge 4$）且前 4 个列下标 ci 完全重合时，置 near = true。
  • 奇数 Wave 早退释放与双行共载：一旦确认 near == true，偶数行组对应的奇数 Wavefront（wy & 1）直接提前返回；留下的偶数 Wavefront 每轮把同一个列索引对应的 float4 稠密向量从 B 读入寄存器一次，同时喂给 acc0 与 acc1 两行的乘加，直接减少一半 B 矩阵带宽压力。若第 5 个非零元起突发列号分叉（mismatch），代码立刻平滑退回各自的独立尾部扫描，既拿了块稀疏收益，又确保结构误判下绝不算错。
  • 循环展开与宽度特化：小/中宽常规分支调用 vector4_original_p4（16 路主循环展开 + 4 路次级展开 + 尾部收尾）；当 N >= 512 对齐时切入 csr_wave64_scalar_dual4 / dual4_full，让单个线程寄存器组同时覆盖 2 个 float4 块（Tile512，主循环 8 路展开）；N >= 1024 进一步切入 csr_wave64_scalar_quad4（Tile1024），减少整轮稀疏索引扫描次数。

2.4 非对齐回退中的 csr_fp64_heavy_wide8 与静态 LDS 权衡

在无法走 float4 向量路径的宽矩阵回退（!aligned4 && N > 256）上，Round 12 没有简单写个朴素标量循环敷衍过去，而是接入了带高精度误差自检的 csr_fp64_heavy_wide8<8>（Block (32, 8)，一组 32 线程负责宽度切分，8 个逻辑行组成 CTA）：

  • 无重行先验退避：进入内核第一件事就是读取 rp[group_end] - rp[group_begin]，若整个 8 行 CTA 非零元总数 $< 1024$（或 fp64_split_select_owner 判定没有 $\ge 1024$ 且达次大行 $4\times$ 的超重行），不经任何 CTA 屏障直接走 fp64_split_original_coop_row，按原版 FP32 顺序算完退出。
  • 8 槽协分与误差边界判定：确有孤立超重行时，8 个逻辑行槽共同分摊这 1 条超重行并以 double 累加同时记录绝对值乘积和 magnitude_total；归约后计算误差界 difference_bound（基于 4.0 * DoubleEpsilon * maximum * magnitude_total），与原 FP32 误差容限比对：如果不会触发严重误差漂移就直接转回 FP32 写出；只有在检测到潜在严重正负相消风险时，才针对该列回退重算。
  • 如实指出的副作用：正如源码注释里自我审计注明的一样，由于该内核声明了 __shared__ double partial[8][8][32]、absolute_sum[8][32] 与 lengths[8]（合计约 18 KiB 静态 LDS），即使运行到提前退出的普通短行 CTA，硬件调度器仍会在占满约束计算中计入这笔静态共享内存声明。这也是为什么我们将它严格隔离在非对齐宽表回退路径，而不让三大对齐快路径沾染任何静态 LDS。

此外，ns_spmm_fused_mask 也补上了 K == 0 时的全输出清零（hipMemsetAsync）保护，并用 __builtin_ctz + m &= (m - 1u) 快速跳过零掩码位，避免无效内层乘加。

3.2 与上一代高性能版（38235757）6 轮配对盲测（BW gfx936）

为了检验融合修改不是只在跟慢基线比，团队还在同机跑了 6 轮严格配对对比（对照上一版高优化版本 38235757），最终 6 算例几何平均（GM）再提速 1.224x：

  • longtail_1024x1024x256_d5：中位耗时由 0.080542 ms 压缩至 0.027811 ms（2.904x）；
  • block_1024x1024x256_d25：由 0.069770 ms 降至 0.063601 ms（1.097x）；
  • 其余 4 组：uniform_d50（0.112090 -> 0.109580 ms, 1.023x）、misaligned（0.010049 -> 0.009919 ms, 1.022x）、extreme_1pct（0.021852 -> 0.021731 ms, 1.008x）与 uniform_d10（0.164325 -> 0.164269 ms, 1.000x）全部保持持平微增、零回归。

3.3 验证覆盖实录与筛选舍弃项

  1. 公开套件与 verify.sh 独立工具：
    • 公开测试 public.log 共 18 项正确性校验（4+6+8）全部 PASS。
    • independent.log 独立工具链实测通过：Stage3 111 个静态算例 + 56 个动态帧、既有 16 帧动态模式切换与短行正负相消组合、27 个重行位置迁移算例与动态同地址复用帧，以及 24 组 ns_spmm_fused_mask（覆盖 K=0/1/31/32/33/65 与对齐/非对齐宽度） 探针全数 PASS。
  2. 未合并的负收益实验记录：交付排查阶段还实际测过短行两路流水（short2）、共享内存转置（layout）、二者叠加（short_layout）以及显式 __launch_bounds__ 约束（lb4/lb8）共计 5 个候选项，对比 Round 12 在 6 算例或最差单测比上均表现为持平或轻微负收益，因此全部记录在案并保留原主干未强行并入。

四、 已知边界与遗留说明

复盘完这轮重构，把当前代码客观存在的适用范围边界写清楚：

  1. 对齐快路径的数值舍入前提：除了 use_strided && N % 256 == 0 拆行片段与 csr_fp64_heavy_wide8 局部用了 double 累加之外，主流 csr_wave64_scalar_* 向量内核在寄存器中仍按常规 FP32 累加。对于自然训练权重或随机分布测试误差极小，但若遇到人为构造的极端动态范围正负大数相消矩阵且刚好命中共对齐快路径，仍可能超出 FP32 逐次累加容差。
  2. use_strided 的首行假设边界与 wide8 静态 LDS：如前所述，use_strided 通过头部 deg0/deg1 判定实现 $O(1)$ 零全局代价开销，并不扫描整张稀疏表；同时 csr_fp64_heavy_wide8 带有的约 18 KiB 静态共享内存只局限于 N > 256 非对齐回退路径。
  3. 跨平台泛化待补充实机运行：gfx906 端仅验证了通过编译器前端与代码生成（exit 0），其具体的 Occupancy 与实机绝对耗时待有机会重上 Z200 后再单独补测，不在本文中把 BW 数据直接外推过去。

比起早期堆砌一堆炫酷寄存器概念却没对上哈希的版本，这一轮真正静下心把正负相消边界、动态重行和配对 ABBA 逐一核实完，才算把代码里自己真掌握的东西稳稳留了下来。
