深入海光 DCU 异构计算：动态稀疏矩阵乘 (SpMM) 的 Wave64 标量化与 100% Occupancy 极限调优

发表于 2026-11-09 分类于 技术实践

接上一篇关于 Qwen2.5-1.5B 端侧超长上下文推理底座的总结，这篇继续整理本次先导杯（CSCC）校内选拔赛的第二道核心赛题——面向神经-符号融合大模型的动态 CSR 稀疏矩阵乘稠密矩阵（SpMM, $C = A \times B$）算子极限优化。

yysy，以前上专业课学计算机组成原理和体系结构的时候，总觉得什么寄存器溢出（Register Spilling）、缓存写分配（Write Allocate）、指令级并行这些概念离自己十万八千里，应付完期末考试就差不多还给老师了。直到这次真刀真枪去压榨海光 DCU（gfx906）的每一微秒延迟，才发现课本上枯燥的硬件指标全都变成了实打实的性能天花板。现在的 AI 辅助工具确实能帮我们快速生成内核代码骨架，但涉及到“为什么加了双 CTA 反而变慢”、“怎么把 VGPR 死死卡在 24 个以内”这种硬件微架构层面的博弈，最终还是得靠扎实的实验剖析和物理建模来拍板。

最终，我们的算子在官方 6 组公开基准算例上的总耗时从基线的 10.367 ms 压降至 1.431 ms（综合加速比达 7.24x），并在包含 370 项极端边界与动态流压力测试的工业级门禁中实现 100% PASS。下面详细拆解核心的四个微架构优化层次。

一、 问题背景与硬件微架构瓶颈剖析

1.1 算子定义与动态稀疏挑战

给定以标准 CSR（Compressed Sparse Row） 格式存储的稀疏矩阵 $A \in \mathbb{R}^{M \times K}$（包含 row_offset、col_indices、values 三个一维数组）与行主序稠密矩阵 $B \in \mathbb{R}^{K \times N}$，我们需要计算稠密输出矩阵 $C = A \times B \in \mathbb{R}^{M \times N}$，并支持神经-符号融合场景下的动态掩码过滤接口（ns_spmm_fused_mask）。

不同于稠密矩阵乘（GEMM）拥有规整的访存步长与极高的计算访存比，动态 SpMM 面临三重天然劣势：

  1. 极端的负载倾斜（Load Imbalance）：在长尾分布（longtail）与极端聚簇（extreme）算例中，部分重行（Heavy Rows）包含数千个非零元（NNZ），而大量轻行仅有寥寥数个非零元，极易引发严重的计算单元（CU）尾效应。
  2. 随机访存与带宽受限（Memory-Bound）：读取稠密矩阵 $B$ 的行索引依赖于 col_indices[idx] 的运行时间接寻址，导致 L1/L2 Cache 命中率骤降，350+ 周期的 HBM2 访存延迟完全暴露。
  3. 寄存器压力与占用率崩塌（Occupancy Collapse）：在 AMD GCN5（gfx906）架构下，每个 SIMD 单元拥有 64KB（即 16,384 个 32-bit）矢量寄存器（VGPR）。由于 gfx906 采用 Wave64（64 线程/Wavefront） 机制，一旦单个线程使用的 VGPR 超过 25 个，每个 SIMD 可并发驻留的活跃 Wave 数量就会从满载的 10 Waves 断崖式跌落，直接削弱硬件隐藏访存延迟的能力。

二、 核心优化一：Wave64 CSR 标量化与寄存器极限瘦身

在常规的 HIP/CUDA 线程映射中，Wavefront 内的 64 个线程通常协同处理稀疏矩阵 $A$ 的同一行（或相邻双行），沿稠密矩阵 $B$ 的列维度 $N$ 进行向量化展开。

2.1 __builtin_amdgcn_readfirstlane 标量提权

我们观察到：当同一个 Wave64 协同计算稀疏矩阵的同一行时，行起止偏移 row_start / row_end、当前非零元列号 col_idx 以及稀疏权重 val 对于整个 Wavefront 内的 64 个线程而言是完全一致的均匀变量（Uniform Variables）。

如果将这些变量保存在普通的 C++ 局部变量中，编译器默认会将其分配至每个线程私有的 矢量寄存器（VGPR），不仅白白浪费了 $64 \times$ 的寄存器空间，还需要频繁发射 ds_swizzle 或 ds_bpermute 指令在 LDS/通道间进行广播。

为此，我们深度调用了 GCN 架构内建原语 __builtin_amdgcn_readfirstlane：

  • 强制将公共的行索引、非零元列坐标及标量基址从 Lane 0 提取并压入 标量寄存器（SGPR） 与标量算术单元（SALU）；
  • 稠密矩阵 $B$ 的行首指针计算 row_ptr = B + c * N 完全在标量流水线中完成，彻底消除了 64 份重复的 VGPR 占用与跨道洗牌开销。

三、 核心优化二：4×4 Burst Unroll-16 突发加载流水线

针对稠密矩阵 $B$ 间接寻址带来的 ~350 周期 HBM2 高延迟，单纯依靠提高 Wave 占用率（Thread-Level Parallelism, TLP）仍不足以喂饱 1024 GB/s 的显存带宽。我们必须在单线程内部挖掘极致的 内存级并行（Memory-Level Parallelism, MLP）。

在主战内核 vector4_original_p4 中，我们构建了 4×4 Burst Unroll-16 突发加载流水线：

  1. 128-bit 向量化宽加载：每个线程单次操作通过 float4（即底层 global_load_dwordx4 指令）连续读取 $B$ 矩阵同一行的 4 个 FP32 元素；
  2. 4 路突发连续发射（Burst Issue）：在展开因子为 16 的主循环中，将每 4 个非零元编为一个 Burst Group。编译器在生成汇编时，会连续发射 4 条独立的 global_load_dwordx4 指令而不在中间插入任何存在数据依赖的 v_fma_f32 乘加指令；
  3. VMEM 队列深度掩盖延迟：这 4 个 128-bit 读请求被同时压入硬件的 VMEM 访存队列并行飞向 HBM2 控制器，待数据返回寄存器堆后再集中执行 FMA 累加，将整个内核的 VGPR 严格控制在 29 个（0 Spill）。

实机评测表明，仅这一项突发流水线改进，就使高密度算例 uniform_1024x1024x256_d50 的延迟从 0.501 ms 暴降至 0.440 ms（算力跃升至 610.03 GFLOP/s，达 4.79x 加速），block_1024 算例更是飙升至 0.102 ms（1344.74 GFLOP/s，10.42x 加速）。

四、 核心优化三：$N=512$ 零分支成对加载与 100% 满占用特化

在优化宽矩阵算例（$N=512$，如 uniform_2048 与 extreme_2048）时，我们遇到了一个非常反直觉的性能陷阱：

4.1 为什么“双 CTA 空间切分”在 $N=512$ 上反而变慢？

最初的直觉是：既然单 Wave64 每次 float4 只能覆盖 $64 \times 4 = 256$ 列，那么当 $N=512$ 时，直接开启 grid.y = 2（用两个线程块分别处理前 256 列和后 256 列）岂不是刚好提高并发？

然而实机测试狠狠打了脸：开启 grid.y = 2 后，uniform_2048 的耗时不仅没降，反而从 0.680 ms 恶化暴涨至 1.169 ms！
通过剖析硬件行为，我们找到了真凶：当两个独立 CTA 切分同一行的左右半区时，两个 CTA 都必须从头到尾完整扫描一遍该行的 CSR col_indices 与 values 数组，导致稀疏元数据读取流量翻倍，且在重行上引发了严重的 L2 Cache 争用。

4.2 csr_wave64_scalar_dual4_full：24 VGPR 实现 100% Occupancy

为了在单 Wave 内一次性吞下 $N=512$ 的全部列且不触发寄存器降级，我们专门设计了零分支特化内核 csr_wave64_scalar_dual4_full：

  1. 彻底剔除列边界分支：由于已知 $N=512$ 恒定，单线程负责相距 256 列的两个 float4（即 j0 = lane_id * 4 与 j1 = j0 + 256），直接移除了内层循环中所有的 if (j0 < N) 动态谓词判断与 EXEC 掩码切换指令；
  2. 硬件立即数偏移复用基址：两个 float4 之间恰好固定相距 $256 \times 4 = 1024$ 字节。我们直接复用同一个标量行基址 row_ptr = B + c * 512，令第二条加载指令利用 GCN 硬件原生的立即数偏移寻址 offset:1024 发射成对的 global_load_dwordx4，省去了维护第二套地址寄存器的开销；
  3. 卡死 24 VGPR 黄金红线：经 hipcc --save-temps 编译器实测核验，该内核的矢量寄存器占用被精准定格在 24 VGPRs（0 Spill）！在 gfx906 上实现了 10 Waves / SIMD（即 100% 理论极限满占用率）。

五、 核心优化四：非时间局部性流式写回与中宽长尾自适应

  1. 绕过 L2 写分配（Non-Temporal Store）：
    输出矩阵 $C \in \mathbb{R}^{M \times N}$ 在写出后直到内核结束都不会被再次读取。如果走常规缓存写回，硬件会触发 写分配（Write-Allocate），把宝贵的 8MB L2 Cache 污染并挤占殆尽。我们在写回阶段显式调用 __builtin_nontemporal_store（生成底层 global_store_dwordx4 ... glc slc 流式指令），绕过 L2 直接流式写回 HBM2，将全部 8MB L2 Cache 留给高频复用的稠密矩阵 $B$，实现了约 1.2x 的有效带宽放大。
  2. 中宽长尾算例的双 CTA 空间并发（Tile256）：
    针对非零元极度集中但行数适中的中宽长尾算例（如盲测集中的 wmh22），单 Wave 处理整行会导致严重的 CU 空闲。我们通过启发式门限动态开启 Tile256 双 CTA 空间并发，使该类算例耗时从 0.2730 ms 骤降至 0.1404 ms（提速 1.945x）。

七、 总结
