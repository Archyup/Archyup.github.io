面向端侧与国产 DCU 环境的 Qwen2.5-1.5B 推理优化：32K 长上下文 KV 复用与静态图调度实践

发表于 2026-11-09 更新于 2026-11-13 分类于 技术实践

好久没更新博客了。从大一刚入学参加岳麓黑客松时跟着学长学怎么调 API，到现在大二上学期扎进先导杯（CSCC）调海光 DCU 上的大模型推理，这一年的跨度比我预想得大一些。

yysy，放在以前，让一个刚上大二的本科生去读 transformers 底层注意力源码、改 HIP C++ Kernel、抓 Graph Capture 时序气泡，光查文档就很容易劝退。现在用 AI 辅助写样板代码、查 ROCm 编译参数确实省掉了很大一部分信息差；不过真到做技术方案和实验验收时，哪些融合真带来加速、哪些显存省在哪儿、哪些精度会暗地里漂移，还是得老老实实盯硬件约束、写对比实验、对着实机日志一条条核对。

这篇文章复盘先导杯第一题围绕 Qwen2.5-1.5B-Instruct 所做的推理优化实践，并在 11 月 12 日完整核验与代码审计之后，把早期草稿里混杂的不同硬件口径、不严谨的“零开销”表述以及未标注边界的地方全部修订成经实测日志核验的真实记录。

一、 赛题约束与测试基准说明

先交代清楚背景与硬件口径，避免把不同机器的数据混为一谈：

  • 赛题背景：围绕 Qwen2.5-1.5B（FP16、28 层、12 Query 头、2 KV 头、Head Dim 128、Hidden 1536、Intermediate 8960），同时考核短/中文本批处理吞吐延迟（A/B 集）以及接近 32K~32.5K 上下文的超长序列推理（C 集，受端侧 16GB 显存与 OOM 边界约束）。
  • 本文对齐硬件与软件环境：本文全部最终数据均来自 11 月 12 日归档的交付包 team_submission 在海光 BW（gfx936:sramecc+:xnack-，可见显存 63.98 GiB） 实机上的完整验证；软件栈为 Python 3.10.16、PyTorch 2.4.1、HIP 6.1.25065、Transformers 4.46.3、DTK 25.04。早期测试草稿中出现的另一套 Z200（gfx906）数据对应旧版源码，未与最终集成 mlp_gemv_probe.hip 的版本重新实测对比，故本文不再混用。
  • 官方基线执行特征：基线实现（hf_sdpa_math_chunked_prefill_v2）已包含 prefill_chunk_size=1024、DynamicCache、num_logits_to_keep=1、SDPBackend.MATH（强制对齐数学参考精度）及每步有限性检查（every_forward_finite）。

面对这套基准，短请求慢主要卡在 Python 框架调度和每步重复启动大量小 Kernel（Launch Overhead），以及 RoPE、RMSNorm、SiLU 等逐元素算子的反复全局内存往返；长文本则要求在显存可控的前提下稳定跑过 32.5K。系统整体拆成了两套路径：



flowchart TD
    IN["输入 Batch 请求"] --> ROUTE{"输入与生成总长不超过 300?"}
    ROUTE -- "是（短文本走静态图池）" --> POOL["ExactPrefixGraphPool\n（4 条常驻 Lane 线程 + work_queue）"]
    POOL --> PRE["PrefillGraphBank（width 1..64）或 Eager Prefill"]
    PRE --> DEC["Decode 静态图回放（REPLAY_CHUNK=8）\nExactPrefixCache 预扩展 12 头 KV"]
    ROUTE -- "否（超长文本 / 32K C 集）" --> LONG["_generate_chunk 通用路径"]
    LONG --> CHUNK["1024-token 分块 Prefill\n无 Padding 时跳过 4D Mask"]
    CHUNK --> KEEP["每块 num_logits_to_keep=1 有限性校验\n+ Standard Decode"]

二、 核心优化实现与工程权衡

2.1 长上下文分块 Prefill 与无 Padding Mask 省略

长文本路径（_generate_chunk）并没有搞玄学，主要做了三件干净的减法：

  1. 分块尺寸解析与自适应开关：默认沿用 PREFILL_CHUNK_SIZE=1024 切片处理宽序列（超过 chunk_size 时分块推进 DynamicCache），同时代码中保留了 PREFILL_CHUNK_SIZE=auto 选项，当可用显存 $\ge 12\text{ GiB}$ 时切到 2048 减少 Python 分块循环次数。
  2. 只保留块尾 logits 检查，而非跳过 lm_head：早期总结里误写过“跳过前 31 块 lm_head”。实际检查 native_027.py 代码可知，为了与官方基线 every_forward_finite 对齐，for chunk_start in range(0, width, chunk_size) 中每一块调用 self.model(...) 都传入 num_logits_to_keep=1，然后对返回的尾 token logits 调用 require_finite_logits。这样做的作用是避免一次性实例化 [batch, chunk_size, 151936] 的全词表巨大张量，而不是把中间块的非有限值检查删掉。
  3. 无 Padding 省略 4D Mask 缓冲：当单条或等长批处理不需要左填充 Padding（has_padding == False）时，mask_buffer 直接置为 None，省掉长序列下额外构造维护的 (batch, width + max_new_tokens) 注意力掩码。

在 C 集 4 条长文本（上限 32K~32.5K 上下文范围，max_new_tokens=256）实测中，PyTorch 进程峰值已分配显存为 5797.74 MiB（约 5.66 GiB），kv_cache_oom 为 false。需要遵循审计说明标明口径：该指标是 PyTorch 进程侧测得的峰值已分配显存（包含模型权重与推理激活），既不等于纯粹 KV Cache 独占大小，也可能未计入部分外部运行时底层分配。

2.2 静态 HIP Graph 池：元数据复用、REPLAY_CHUNK=8 与内存代价

短请求的 Decode 阶段一次只算一个 token（M=1），如果不做静态图，每步都要经过 Python 调度几十层的 PyTorch 算子发射，时间全耗在 CPU-GPU 发令间隙里。

native_027.py 围绕 ExactPrefixGraph 与 ExactPrefixGraphPool 做了以下调度改造：

  • 4 路常驻 Capture 线程 + 私有 BLAS 句柄：ExactPrefixGraphPool 默认开启 PREFIX_GRAPH_LANES=4、PREFIX_GRAPH_CAPACITY=300（预留位置覆盖 prompt + decode 总长 300 内），并为每个 Lane 配一条单线程 ThreadPoolExecutor 长期保持线程存活，防止临时线程销毁或切换导致底层 rocBLAS/hipBLAS handle 重建错乱；批量请求通过 work_queue 动态派发到空闲 Lane。
  • PrefillGraphBank 覆盖小宽度 Prefill：默认启用 PREFIX_PREFILL_GRAPH=1 时，每条 Lane 还会针对 width = 1..64 预先捕获 64 张固定宽度 Prefill 静态图，使短输入的 TTFT 也摆脱 eager launch 气泡。
  • 元数据指针重置 KV Cache（PREFIX_CLEAR_KV=0）：每条 Lane 的 ExactPrefixCache 静态申请了 key_cache12 / value_cache12（形状 (28, 1, 12, 300, 128)）。关闭清零后，跨请求复用不再调 .zero_() 刷整块显存，只重置 past_length 与 visible_length：新请求的 Prefill 会直接覆盖 [0, width) 槽位，Attention 只切片读取 [:visible_length]，历史残留槽位位于因果掩码和可见窗口之外。
  • 批量异步回放 REPLAY_CHUNK=8（带必须说明的代价）：Decode 循环不再每生成 1 个 token 就同步 .item() 拿回 CPU，而是在静态图里把每次采样 token 与 torch.isfinite 标志写入预设的 token_history / finite_history 显存缓冲，默认按 CHUNK=8 连续发射 8 张 Graph 后做一次 .tolist() 回传检查。
    • 客观纠偏：早期版本宣传“REPLAY_CHUNK=8 彻底消除了 EOS 后的无效步”。实际从 generate_encoded 代码来看恰恰相反：如果序列在某个 Chunk 中间第 $k$ 步已经吐出 eos_token_id，同一个 Chunk 里剩下的至多 7 步 Decode Graph 依然已经在 GPU 上发射并执行完，而且这部分计算时间全算在端到端统计窗口内。CHUNK=8 真正换来的是把原本每步 1 次的 CPU-GPU 同步等待摊薄为每 8 步 1 次，是以少量冗余算力换同步延迟的折中设计。

此外，这套多路静态图设计有明确的初始化与内存代价（直接记录自 delivery_package_validation.log）：

  • 启动初始化耗时 322.05 s（需为 4 条 Lane 各捕获 299 张 Decode 图 + 64 张 Prefill 图）；
  • 捕获期间 PyTorch 保留显存（reserved）从 3,441,426,432 字节（约 3.20 GiB）上升至 7,438,598,144 字节（约 6.93 GiB）（相当于额外占下约 3.72 GiB 静态图与缓存保留空间）。在 64GB 的 BW 卡上很充裕；如果直接迁移到严格只有 16GB 的端侧设备再叠加上下文缓存，必须下调 PREFIX_GRAPH_LANES 或压缩容量上限，否则静态图池本身就会挤压长文本可用空间。

2.3 rope_exact.hip、candidate_support.py 与权重合并打包

在算子层，主要通过 candidate_support.py 对 transformers 里的 Qwen2SdpaAttention.forward、Qwen2DecoderLayer.forward、Qwen2RMSNorm.forward、Qwen2MLP.forward 等入口进行 Monkey-Patch，在保证输入条件满足（FP16、contiguous、无梯度）时切入自研 HIP C++ 算子（编译参数明确强制关闭激进融合优化：-fno-fast-math -ffp-contract=off）：

  1. 位级对齐的 RoPE 与归约型 Add-RMSNorm（rope_exact.hip）：
    • rope_exact_f16_kernel 将旋转位置编码中的两项乘积分别显式执行 __float2half_rn(...) 截断回半精度后再相加，复现 PyTorch Eager FP16 的舍入顺序。
    • add_rmsnorm_exact_1536_kernel<BW>（以及独立版 rmsnorm_exact_1536_kernel<BW>）把 residual + hidden_states 与随后的 RMSNorm 合并为一个 Kernel；实现上按 ATen thread_reduce_impl 写 4 路局部求和再通过 __shared__ float shared[BW] 归约树完成块内规约（根据 rows 在 256/128/64 线程块间分档），并没有使用 Wave64 shuffle 改变加法结合序，以此稳住短文本逐位对齐。
  2. 12 头 KV Cache 写入时预展开（kv_update_repeat6_f16_kernel）：
    • Qwen2.5-1.5B 采用 GQA（12 个 Q 头，2 个 KV 头，n_rep=6）。每次 Attention 计算都调一次 repeat_kv 会产生额外的拷贝内核发射。
    • 在走静态图池的 ExactPrefixCache 中，kv_update_repeat6_f16_kernel 在把本步生成的 2 个 KV 头写入静态 Cache 时，直接循环 #pragma unroll 展开到连续的 12 头槽位（h12 = h2 * 6 + r）；随后 Attention 主流程调 apply_repeat_kv 时，只要检测到 hidden_states.shape[1] == 12 就直接原样透传返回。长序列分支用 DynamicCache 时仍安全回退原路径。
  3. 关于 torch.cat 权重融合与“0-VRAM”标签的纠偏：
    • prepare_model 将每层的 q_proj/k_proj/v_proj 权重拼接为 _packed_qkv_weight（Decode 单 Token 走一次 linear 再切片分头），并将 MLP 的 gate_proj/up_proj 拼接为 (17920, 1536) 的 _packed_gate_up，随后用 .narrow() 视图把原来的 nn.Parameter 指向新连续内存，最后 gc.collect() + torch.cuda.empty_cache()。
    • 必须明确说明：虽然推理稳态下的投影共享了同一份权重存储，但在模型初始化执行 torch.cat 那一瞬间会存在一次拼接所需的瞬态额外显存峰值（需要旧分片与新整块同时短暂驻留再回收），并非绝对意义上完全零额外显存占用。此外，candidate_support.py 里虽包含 W8A16Linear（可通过 QUANTIZATION=int8 或 w8a16 开关激活的权重量化预留接口），但本次交付验证默认全部走原精度 FP16 路径，未启用该量化实验开关。

2.4 最后一公里的 gate_up_gemv_silu（mlp_gemv_probe.hip）

11 月中旬对比 Profiling 后，我们发现前面 28 层的 QKV 与 RoPE 融合完成后，单个 Decode token 阶段占比最高的小算子落到了 MLP 上半段的 gate_proj、up_proj 与 SiLU(gate) * up 三连跳。

为此在 mlp_gemv_probe.hip 里加了一个专门接管 Decode 单 token Contiguous FP16（x.numel() == 1536）的融合 GEMV 算子 gate_up_gemv_silu：

在单层微基准测试（mlp_microbench.json，Layer-0 实权重，单流 Graph Replay）里，单次 MLP 前半程执行时间从基线 0.1488 ms 降到 0.0892 ms（约 -40.1%），8960 维输出中有 8946 个元素与 PyTorch 基线逐位相等，最大绝对偏差 1.22e-4（由于改变了 FP32 点积融合累加顺序并在输出 SiLU 相乘前做 __float2half_rn 截断所致）。

3.2 必须写清的正确性边界与未解决事项

做系统优化最怕只报加速比、把边角分歧藏在桌底下。经多轮审计后，这版代码在正确性与门禁覆盖上明确存在三条边界：

  • A 集与 C 集完全对齐，Inject 测试通过：A 集单条 10/10、A 集批量 10/10 的 exact_match_rate 均为 1.0；C 集 4 条长上下文位置匹配率（position_match_rate）为 1.0。另外在 mlp_real_nonfinite_probe 中向 Decode Graph 注入 NaN/Inf 后，成功抛出了 FloatingPointError("Non-finite model logits in graph decode")，证明异常保护仍在生效。
  • B 集 10 条样本中存在 2 条离散 token 分歧：在公开 B 集 10 条 × 256 步生成对比中，候选方案与不带 gate_up_gemv_silu 的对照版本相比，第 3 条样本（第 137 步）与第 5 条样本（第 69 步） 出现了 argmax 选词分歧，其余 8 条全对齐。根因正是融合 GEMV 改变了 gate/up 的浮点累加结合序，单层 1e-4 量级的极微差异在长程自回归中遇到次高概率非常接近 Top-1 的位置时翻转了选词。是否接受这类分歧取决于评测集容忍度。
  • 阈值口径属于练习策略而非正式终审：本次 C 集检测所依据的 0.98 最低位置匹配率来自本地练习策略文件 practice_policy.json（策略文本备注明确说明 “仅供学生练习……正式阈值以组委会后续公布为准”，官方正式评判策略中的 C 集阈值彼时尚未设定）。因此这个 PASS 只代表符合本地练习门禁，不能外推表述为“官方终评完全验收”。

回头看这题最大的收获，不是把吞吐从 30 多拉到 169 的数字本身，而是在最后两次审查里亲手把“看似无代价的 0-VRAM”、“以为能停掉 EOS 尾巴的 REPLAY_CHUNK”、“微米级误差会如何传导成第 69 步的 token 分歧”全拆了一遍——知道每一毫秒加速是用什么假设和代价换来的，比单纯挂个加速比靠谱得多。
