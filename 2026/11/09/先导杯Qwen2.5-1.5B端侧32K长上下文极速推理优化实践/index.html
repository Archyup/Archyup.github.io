面向端侧硬件的 Qwen2.5-1.5B 极速推理优化：32K 超长上下文显存极限压缩与静态图调度实践

发表于 2026-11-09 分类于 技术实践

好久没更新博客了。从大一刚入学参加岳麓黑客松时连 API 调用都要抱学长大腿，到现在大二上学期一头扎进先导杯（CSCC）搞海光 DCU / AMD 异构计算与大模型底层推理优化，这一年的跨度确实有点大。

yysy，放到两三年前，让一个刚上大二的本科生去手搓 HIP 算子融合、扣 Wave64 寄存器和 HBM2 访存带宽，几乎是不可能完成的任务。但现在处于 AI 大爆发的时代，AI 某种程度上抹平了底层语法和繁琐工程细节的信息差，让我们学生有机会直接跳过漫长的“造轮子”蓄力期，直接站到系统架构设计、性能瓶颈剖析和严格评测验证的一线。

这篇文章主要复盘并沉淀一下近期在先导杯校内选拔赛中，围绕 Qwen2.5-1.5B 超长上下文（32.5K）端侧极速推理底座 所做的一系列软硬件协同优化实践。

一、 背景与问题定义：端侧 16GB 显存红线下的长程推理困境

1.1 硬件边界与性能痛点

在本地端侧网关或单卡边缘计算场景中，显存容量与访存带宽往往是不可逾越的物理红线。本次优化的目标硬件涵盖两类典型的海光 DCU（兼容 AMD ROCm 生态）平台：

  • 海光 DCU Z200SM_80（gfx906 架构）：64 个计算单元（CU），配备 16GB HBM2 显存（4096-bit 位宽，理论峰值带宽 1024 GB/s）。
  • 海光 DCU BW（gfx936 架构）：配备 64GB HBM2 显存，具备更强的双精度与张量吞吐能力。

当我们将 Qwen2.5-1.5B 模型置于 32.5K（32,768 Tokens） 的超长上下文多轮交互场景时，原生 PyTorch / HuggingFace 推理管线会瞬间暴露两大瓶颈：

  1. 显存爆炸（OOM）：在 32.5K 序列长度下，全量中间激活值（Activations）、未压缩的 KV Cache 广播副本以及词表投影层（lm_head）产生的临时大张量，会使峰值显存飙升至 >75GB，在 16GB 端侧设备上直接触发 OOM；即便开启官方基础分块优化，峰值显存仍高达 8.45GB。
  2. 高频交互迟滞：Decode 阶段属于典型的 访存受限（Memory-Bound） 型负载（$M=1$ 的 GEMV 运算），频繁的小内核发射（Kernel Launch）与 Host-Device 同步气泡导致 GPU 计算单元大量空转，逐词生成延迟（TPOT）居高不下。

1.2 工业级保真约束：0-ULP 逐 Token 绝对对齐

不同于常规业务场景允许一定的近似误差，本次优化设定了极其严苛的正确性门禁：

  • 采用贪心解码（Greedy Decoding），最多生成 256 个新 Token（遇到 EOS = 151645 立即截断并保留该 Token）；
  • 短文本测试集（Dataset A，10 条）必须实现单条与批量推理的 10/10 0-ULP（Unit in the Last Place）逐 Token 绝对一致；
  • 超长上下文测试集（Dataset C，4 条 32K 样本）位置匹配率需达到 1.000（远超官方 0.98 阈值）。

这意味着任何破坏 IEEE 754 浮点归约顺序的激进近似（例如在 $M>1$ 时随意合并矩阵乘输出维度改变 2D Tile 归约树）都会引发 1-ULP 漂移并在长序列自回归中被指数级放大。

二、 显存断崖式压缩：KV Cache 动态架构与计算旁路

为了在 16GB 显存红线下留出充足的多任务余量，我们对推理全生命周期的显存分配进行了重构，将 32.5K 峰值显存从官方基线的 8.45GB 进一步压降至 4.3GB ~ 5.68GB。

2.1 原生 12-Head KV 缓存与 GQA 跨步广播原位融合

Qwen2.5-1.5B 采用了 分组查询注意力（Grouped-Query Attention, GQA） 架构：包含 12 个 Query 头，但仅有 2 个 Key/Value 头（分组比 $G = 6$）。

在原生实现中，每步注意力计算前都需要调用 repeat_interleave 将 2 个 KV 头显式复制扩展为 12 个头以对齐矩阵乘维度。在 28 层 Transformer 结构下，这意味着每步推理都要额外发生 56 次显存张量搬运与临时缓冲分配。

为此，我们编写了自定义 HIP 内核 kv_update_repeat6_f16 与 rope_kv_update_repeat6_decode_f16：

  • 在预分配的静态连续 KV Cache 缓冲区上，直接以 [Batch, 12, MaxSeqLen, HeadDim] 布局进行管理；
  • 当新 Token 的 2 个 KV 头完成计算后，内核在写入静态缓冲的同一条访存指令周期内，利用线程块映射一步完成 $2 \to 12$ 头的跨步广播写入（Stride Broadcast Write），彻底抹平了运行时的 repeat_interleave 显存拷贝开销。

2.2 分块预填充（Chunked Prefill）与中间块 lm_head 旁路

针对 32.5K 超长输入，我们采用 1024 / 2048 自适应分块预填充（Chunked Prefill），并且针对单条请求直通 attention_mask = None（依靠底层算子原生因果掩码规避数十 MB 的显式三角掩码矩阵开销）。

更关键的一项观察是：在自回归预填充的前 $N-1$ 个分块中，模型的唯一任务是构建并填充 KV Cache，根本不需要预测下一个词。

  • Qwen2.5 的词表大小高达 151,936。如果对全部 32K Token 执行 lm_head 投影（维度 $1536 \to 151936$），仅输出 Logits 张量就会瞬间吞噬近 9.6GB 显存，并产生 14.8 GFLOPs 的无效浮点计算与 14.5 GB 的 HBM 读写流量。
  • 通过在前 31 个分块彻底旁路（Bypass）lm_head，且在最后一个分块仅切片提取序列末尾最后一个 Token（hidden_states[:, -1:, :]）送入词表投影层，我们实现了长文本 Prefill 阶段的零冗余显存占用。

三、 算子融合与零显存视图重绑（Kernel Fusion & 0-VRAM View Rebinding）

在消除显存峰值后，优化的重心转向削减 Kernel Launch 次数与 HBM 往返流量。

3.1 严格 0-ULP 对齐的残差与 RMSNorm 融合：add_rmsnorm_exact_1536_f16

Transformer 每层包含两次残差相加与 RMSNorm 归一化。常规算子融合很容易因为改变浮点数累加顺序而破坏 0-ULP 精度对齐。
我们在自研的 add_rmsnorm_exact_1536_f16 HIP 内核中：

  1. 将残差加法 $x = x + \text{residual}$ 与均方根求原位融合，省去一次完整的全局内存写回与重读；
  2. 严格复刻 PyTorch ATen 底层的向量化加载与蝶形归约树（Butterfly Reduction Tree）顺序，确保 FP32 累加器中的舍入行为与官方基准逐 bit 一致，在通过全部 62 项精度门禁的前提下大幅降低了访存延迟。

3.2 Decode 专属 0-VRAM 权重视图重绑

为什么不能无脑将 q_proj、k_proj、v_proj 拼接成一个大矩阵？
我们在 gfx936 实机测试中发现了一个极其隐蔽的硬件底层特性：当 $M > 1$（即 Prefill 阶段的 GEMM 矩阵乘）时，合并输出维度 $N$ 会改变 rocBLAS 内部 2D Tile 的分块尺寸与归约树路径，从而引入 1-ULP 的浮点精度漂移。

但在 $M = 1$（即 Decode 阶段的 GEMV 矩阵向量乘）时，输出向量的每一个元素都是独立的一维行向量点积，合并输出维度完全不会改变任何一行的归约顺序，100% 保持 0-ULP 绝对一致！

基于这一发现，我们设计了 Decode 专属视图重绑机制：

  • 如果直接 torch.cat 复制一份合并权重，会额外占用数 GB 显存；
  • 我们利用 PyTorch 底层的 UntypedStorage 内存池重排技术，将各层的 q/k/v 权重（合并为 $2048 \times 1536$）以及 MLP 层的 gate/up 权重（合并为 $17920 \times 1536$）放置在物理连续的存储块上，同时暴露独立子视图（供 $M>1$ Prefill 使用）与合并整视图（供 $M=1$ Decode 使用）。
  • 这一设计以 0 字节额外显存开销（0-VRAM Overhead），在每生成 1 个 Token 时直接砍掉了 $28 \times 3 = 84$ 次 GEMV 内核发射！

3.3 单步 RoPE 旋转与 KV 写入融合

在 rope_exact.hip 中，我们将 Decode 阶段（seq_len == 1）的 Query/Key 旋转位置编码（RoPE）计算与上述 12-Head KV Cache 广播写入进一步融合为单个轻量级 HIP 内核（Grid = 14, Block = 128），每生成 1 个 Token 再次省去 28 次 Kernel Launch。

四、 消除主机端瓶颈：多通道常驻静态 HIP Graph 体系

在单步 Decode 计算耗时被压缩至亚毫秒级后，Python 解释器调度与 HIP Driver API 的发射开销成为了新的主要矛盾。

  1. 4 路常驻并发图池（PREFIX_GRAPH_LANES = 4）与容量扩充：
    我们将静态图容量扩充至 Capacity = 300（完整覆盖短文本 Prompt 长度 + 256 步生成预算的生命周期上限）。同时建立 4 条独立的 HIP Stream 静态图通道，配合 queue.SimpleQueue 实现多线程动态工作窃取，无需触发动态重捕获即可 100% 保持单条与批量推理的 0-ULP 一致性。
  2. REPLAY_CHUNK = 8 细粒度回放与锁页内存异步 D2H：
    如果每回放 1 步就同步拷贝 Token ID 回 CPU 检查是否遇到 EOS，PCIe 同步延迟会彻底抵消静态图的收益；如果一次性回放过多步，又会在遇到 EOS 后产生大量无效尾步计算。我们采用 8 步微批次图回放，配合 Pinned Host Memory（锁页内存）进行非阻塞异步 Device-to-Host 传输，彻底消除了 CPU 等待 GPU 的同步气泡。

四、 实机评测与性能收益总结

在海光 DCU Z200（gfx906, 16GB）与 BW（gfx936, 64GB）双平台上，经过三轮 Formal 标准评测取中位数，最终交付版取得了显著的端到端性能突破：

五、 结语与一点个人感悟

回看整个优化过程，最深的一个体会是：高性能计算与大模型推理系统优化，从来不是靠单一的“银弹”，而是对硬件微架构边界、内存层级与数学等价性的极致抠细节。 从发现 $M=1$ 下合并投影不破坏归约树的数学特性，到用 UntypedStorage 省下几 GB 显存，每一步都需要拿真实的 Profiler 数据和严苛的门禁测试说话。

作为一名在校本科生，很庆幸能在这个技术变革的时代，借助先进的工具快速跨越底层门槛，去触碰以前只有资深系统工程师才能接触到的工业级真问题。先把系统跑通、把性能榨干、把每一个优化背后的物理逻辑彻底搞懂，这大概就是属于我们这一代 CS 学生最踏实的进阶路径吧。
