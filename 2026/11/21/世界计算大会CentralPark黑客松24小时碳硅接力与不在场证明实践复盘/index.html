24 小时碳硅接力实战复盘：在世界计算大会用 Neuro-Symbolic 架构打造多 Agent 推理游戏《不在场证明》

发表于 2026-11-21 分类于 学习历程

在上一篇赛前备战文《从 Copilot 单次补全到夜间自主接力》之后，11 月 19 日至 20 日，我正式带着这套工作流思路走进长沙国际会议中心，参加了 2026 世界计算大会 · Central Park 开源智算青年训练营（昆仑元 × AMD）。在 24 小时三段式“现场搭骨架 → Agent 夜间自主开发 → 返场收口封板” 赛制下，基于赛事指定的 GPT-Station 工作站与 KCoder + Baize omni 平台，我和现场组队的队友一起完成了多角色 Agent 审讯推理网页游戏 《不在场证明》（首案《蓝钻庄园：午夜巨响》）。

yysy，半个月前刚看到训练营通知时我心里直打鼓——之前连正经的多 Agent 系统都没完整写过，真怕进场之后当个“气氛组”。等到真坐进赛场，面对 Windows 假 python 别名踩坑、Git Rebase 一把误删 1,860 行前端代码、白泽模型偶发陷入超长思考空转，以及封板前 50 分钟的极限排雷，我才切实体会到：24 小时黑客松真正拼的从来不是把 Prompt 写得多玄乎，而是能不能用接口契约（Contract）、确定性规则边界和自动化回归测试网，把大模型的不确定性牢牢框进工程底座里。

最终交付的《不在场证明》全栈仅依赖 Python 3.9+ 标准库与原生 HTML5 / CSS3 / ES6（零第三方 Python/npm 依赖、零外部 CDN），支持双击一键启动；全套工程通过 120 项离线回归测试（ALL CHECKS PASSED，基线实测 13.151s），并打通了独立剧本审稿器 CLI 与 N2 双分支实机策略验收入口，最终在训练营中斩获 专项奖 · AI 开发者创想奖（¥1,000）。

一、 赛前破局（11.08 – 11.18）：从“不敢碰 Agent”到定调《不在场证明》

1.1 赛制拆解与先造轮子练手

11 月 8 日刚接触到这次黑客松信息时，我一度觉得自己对 Agent 编排和夜间自动接管几乎一无所知。与其干焦虑，不如先把赛前十天当成实战预演：先借着研究“无人值守测试门禁”的契机写出 ACS-Agent 把沙箱隔离、契约约束和自动回归走顺；到了 11 月 17 日，又把官方比赛规则按时间轴和合规红线彻底拆了一遍：

  • 24 小时三段式节拍：11/19 12:00 – 17:30（5.5 小时现场搭框架与配任务）→ 11/19 18:00 – 11/20 09:00（选手离场，Agent 在 GPT-Station 上持续执行，只能通过 KCoder 连接器 远程下发指令与查看反馈）→ 11/20 09:00 – 12:00（3 小时返场检查、修 Bug 与提交封板）。
  • 四维自动评分口径：功能完成度、代码质量、Agent 运行效率、创新度；同时提交件要求“四件套”（完整源码、运行入口、项目说明、演示材料），严禁任何第三方远控软件或绕过连接器的远程操作。

1.2 为什么选多角色审讯推理，而不是套壳聊天框

如果只做一个“大模型套壳聊天问答”，技术上很容易写完，但在评委和玩家眼里毫无记忆点，而且纯自由对话在推理场景下极易“剧透”或“被玩家三句话套出真凶”。

11 月 18 日凌晨，我们定下了 《不在场证明》（首案《蓝钻庄园：午夜巨响》）：玩家以受邀客人身份审讯三位各有隐情、甚至可能互相串供的嫌疑人——寄住庄园的表少爷 S1 陆子昂、掌管钥匙十七年的管家 S2 程曼云、以及策划诡计的远亲 S3 顾言。整个剧本围绕 5 件物证、7 份口供、N1–N5 五个剧情节点 与 两个互相独立的结案证据槽 展开。赛前一天我提前敲定了规格书、跑通了一版原型，并整理了《现场 KCoder 极速复刻手册》，只等进场后在工作站上从零按照契约正式落地。

二、 第一阶段 · 现场开局（11.19 12:00 – 17:30）：契约先行与混合推理引擎落地

11 月 19 日上午来到长沙国际会议中心签到，场馆里一排排 KunlunMeta GPT-Station 工作站已经架好。现场按双人组队机制配对（我们被分到 8 队 · 15 号终端），12:00 哨响后正式开干。

2.1 三小时极速落地：先写 CONTRACT.md 再写业务代码

为了让 KCoder 调度白泽模型时不至于“前后端各写各的、改一处崩三处”，我们在 12:51 初始化仓库后没有直接堆业务界面，而是先把全部接口协议、错误码、状态字段和信息公开边界写进了 CONTRACT.md：

  1. 15:25（提交 7dbe419，+4,330 行）：一次性落地案件核心引擎与全套离线单测——包括进程入口 app.py、剧本 cases/case_01_manor.json、服务端五大模块 server/{engine,role_policy,llm_client,config,collusion}.py 以及 tests/test_{case,engine,gateway,http_verify}.py 四组测试套件。
  2. 16:53（提交 161b22e，+2,075 行）：接通三栏式原生 HTML/CSS/JS 前端界面、进程内存热更新网关配置接口（/api/config/llm），以及带明文密钥扫描的提交包脚本 scripts/package_submission.py。

看一眼 15:18 拍下的赛场显示器：RACE PLAYER 计时器刚走到 03:19:00（距封板还剩 20:40:59），本地 LLM API 网关已经实打实跑出了 15.57M Token（输入 14.15M / 输出 1.42M）、180 次模型请求、181 次工具调用。左边开着 KCoder Studio 与 tests/ 目录逐条盯测试，这种高密度人机协同的压迫感和爽感，比平时写作业拉满好几个量级。

2.2 Neuro-Symbolic 混合推理与多角色 Agent 状态协作

为了兼顾“自由审讯的临场感”与“推理定罪的绝对严谨”，整个系统采用 Neuro-Symbolic（神经符号）混合推理架构——模型负责表演与受限策略选择（Neural），规则引擎负责状态机流转、物证校验与结案裁决（Symbolic）：



flowchart TD
    UI["浏览器三栏前端 (web/index.html + main.js)"] --> HTTP["HTTP 接口与静态服务 (app.py)"]
    HTTP --> ENG["案件引擎 (server/engine.py): 行动点 / 节点解锁 / 角色调度"]
    ENG --> MEM["独立角色问答记录 (按嫌疑人 ID 隔离)"]
    ENG --> STATE["共享会话状态 (已获证物 / 公开口供 / 已触发节点)"]
    STATE --> JUDGE["双槽规则裁决 (time + culprit 独立校验)"]
    ENG -- "对白生成 / 触发 N2 策略节点" --> POL["受限角色策略 (server/role_policy.py)"]
    POL --> GW["白泽模型网关 (server/llm_client.py)"]
    GW -- "未配置 / 超时 / 非合约 JSON" --> FB["离线对白库与默认动作 (source=fallback)"]
    GW -- "合法 JSON 白名单动作" --> ENG

这套底座在实际跑起来时，靠三道硬约束守住了逻辑闭环：

  1. 模型只选白名单策略，自由文本绝不定案：整局游戏把大模型的核心策略决策收束在 S2 程曼云的 N2 节点。触发时，server/role_policy.py 只传四类信息（本轮出示条目、她已公开的说法、玩家原问题、两种合法动作说明），并强制要求返回精确到键名的单字段 JSON {"action_id": "..."}：
白名单动作 触发语境特征 引擎落盘执行的正式结果
maintain_alibi 玩家默认其时间判断，仅核对目击对象 授予 T_S2_MAINTAIN（维持顾言在场互证），后续追问聚焦“能否一直看见顾言”
narrow_claim 玩家锐利拆穿“闻声时刻 ≠ 案发时刻” 授予 T_S2_NARROW（收窄为只确认闻声时在场），后续追问转向“响声为何能代表案发时间”

一旦出现超时、非 JSON、未知动作或携带多余字段，引擎立刻拦截并统一回落到 maintain_alibi（同时把 role_action.source 严格标记为 fallback，绝不允许模型自报 live 状态）。

  1. 多角色 Agent 独立上下文 + 共享案件状态：三位嫌疑人共用模型网关，但服务端按 suspect_id 严格隔离各自的问答记忆与已公开说法；完整案件真相、真凶身份和未解锁线索永远留在服务端，绝不塞进常规对白 Prompt。角色之间的跨角色信息传递，全部通过带固定 ID 的正式口供经引擎验持流转——例如 S1 陆子昂 在 N1 公开证词 T_S1_01 后进入共享会话状态，玩家只有把它实际出示给 S2 程曼云，才能触发 N2 策略与串供告警（server/collusion.py）。

  2. 双证据槽确定性结案与反秒猜机制：为了防止玩家靠数值猜凶手，我们在剧本里刻意设计了生理烟雾弹——无辜偷酒的 S1 陆子昂 起始心率极高，反而策划诡计的真凶 S3 顾言 起始心率最稳。结案时固定校验两个互相独立的证据槽：

    • 作案时间证据槽（time）：需提交 E3（停在 00:05 的发条闹钟），且前置节点 N4 已解锁；
    • 指认证据槽（culprit）：需提交 T_S2_FLIP（程曼云改口口供），且前置节点 N3、N5 已解锁，同时指认对象为 S3。
      同一条目禁止同时填入两槽（直接返回 400 duplicate_evidence），结案后会话立即锁定（后续请求返回 409 session_closed），确保复盘结果 100% 可独立复验。

三、 第二阶段 · 碳硅接力（11.19 17:30 – 11.20 09:00）：Git 抢险、跨端交接与凌晨调教白泽

3.1 傍晚惊魂：1,860 行前端误删抢修与两个 Windows 工程坑

开发不可能一路顺风。17:28–17:30 临近交接检查前，由于一次异常中断的 .git/rebase-merge 状态叠加提交 d72928b，工作区里刚写好的 1,860 行 web/main.js 等前端文件直接被删空。好在当时没有慌乱执行强清指令，而是用三步精准止损：

  1. 先切出备份分支 backup-pre-cleanup 并把关键改动文件复制到系统临时目录保底；
  2. 执行 git rebase --quit 安全退出卡死的 rebase 状态（不回退工作区）；
  3. 从本地提交 e0e5288 把 web/ 与 scripts/package_submission.py 完整检出恢复，并在 tests/test_http_verify.py 里立刻补上一条 test_static_web_assets_served 回归测试——实测 GET /、/web/style.css、/web/main.js 全部返回 200 且首页必须包含 id="evidenceBox"，从此把“误删静态前端还能绿灯”的漏洞彻底焊死。

顺手记下两个只有真在 Windows 工作站上打过比赛才会懂的工程坑：

  • 假 python 别名坑：Windows 终端直接敲 python 容易触发系统商店空壳别名（直接退出 9009），我们在 start_windows.bat 和所有验收文档里全线统一改用 py -3 -B（既绕开假别名，又不污染工作区生成 __pycache__）。
  • 后台端口噪声坑：多进程起停本地端口做 HTTP 验证在赛场机器上极易撞端口、留僵尸进程，后来直接改成同进程起真实 app.Handler 配合真实案件 JSON 做端到端 HTTP 校验，快且零环境噪声。

3.2 交接防线与合规夜间推进

晚上 21:50（提交 b08acf7，+3,482 行），我们把 server/baize_verify.py（N2 双分支实机验收）、独立案件审稿官 scripts/ai_case_auditor.py、HANDOFF.md 以及给负责 UI 润色队友的 TEAMMATE_UI_HANDOFF.md 全部锁入分支。

交接文档里直接划清了前端开发红线：只允许改 web/ 下指定前端文件，严禁修改 CONTRACT.md 与服务端引擎，严禁使用 innerHTML（统一走 textContent / createTextNode），严禁出现外部 CDN、npm 构建和任何密钥前缀字符，每次改动必过 --verify 与 --dry-run 打包扫描双门禁。

夜间撤离场馆后，所有远程指令严格走官方合规通道——飞书 / 企业微信 → KCoder 连接器 → 工作站 分步下发。实战里还摸出一条非常管用的“训白泽”经验：遇到跨多文件的复杂前端任务时，白泽模型偶尔会陷入超长思考空转迟迟不动手写代码；当判断它已经把上下文和方案推导充分后，及时打断当前思考并简明重申核心修改范围与验收目标，它就能迅速收敛切入编码。

3.3 清晨 07:02 的交付惊喜

11 月 20 日清晨醒来拉取状态，Agent 夜间最后在 07:02（提交 996c1cb，+3,110 / -341 行）交出了一份超预期的更新——依然保持 0 外部素材、0 第三方库：

  • 纯原生 SVG 动态剪影舞台（web/avatar_rig.js，575 行）：三位嫌疑人全部用代码绘制暗黑几何剪影，随心率与心理防线（composure）动态呈现微震颤、冷汗与瞳孔变化；当真凶 S3 顾言 防线跌到临界值（composure <= 15）触发 .is-cracked 状态时，镜片裂纹显现、镜框顺势倾斜 -8° 下沉。
  • 本地 Canvas 64×64 玩家侦探头像：在浏览器本地通过像素亮度采样提取轮廓与主色调，即时生成同画风侦探剪影并写入 localStorage，不上传照片也不依赖多模态接口。
  • WebAudio 程序化声学合成（web/audio_synth.js，242 行）：零音频文件，纯振荡器实时合成随心率变化的心跳脉冲与警报音效，静音或不支持时静默降级。
  • 按需网关探测与防重复护栏：把进程健康检查（/api/health）和真实白泽网关探活彻底拆开，并加了单飞锁避免页面刷新重复把网关打爆。

四、 第三阶段 · 返场验收与交付审计（11.20 09:00 – 12:00）：为什么封板前先写了一份“问题报告”？

4.1 三条可独立复现的验收入口

9:00 返场后，我们做的第一件事不是急着加功能，而是把整套验收矩阵一条条跑实：

验收命令 验证范围 是否联网 实测结论与验收标准
py -3 -B app.py --verify 案件结构、行动点、节点排序窗口、HTTP 防剧透、网关回退、双槽裁决 否 120 项全量通过（基线实测 13.151s，提交包副本复测 11.549s，输出 ALL CHECKS PASSED）
py -3 -B scripts/ai_case_auditor.py --selftest & cases/case_01_manor.json --offline 坏剧本拦截自检 + 正式剧本防剧透/引用闭合/高心率烟雾弹硬审查 否（可选 --live） 自检输出 SELFTEST PASSED；正式剧本输出离线硬审查报告 PASS
py -3 -B app.py --probe-baize & --verify-baize 网关 {"ok":1} 连通探针 + 同初始态 A/B 问法触发 N2 真实分流 是 要求两组策略 source == "live" 且分别输出 maintain_alibi 与 narrow_claim，回落 fallback 一律判负；通过输出 LIVE DECISIONS VERIFIED

4.2 封板前的“反吹牛”对抗式自审

离 12:00 封板只剩不到一小时，我们专门针对最终提交包跑了一轮对抗式交付审计（Delivery Audit），先自己给自己挑出了一份详细的《不在场证明_问题报告》，再去打磨最终的《项目说明报告》：

  • 查出真实前端细节问题：比如及时关闭了 P1-01（保证 N2 关键回合及快捷追问真实可用、结案卷宗在窄屏完整滚动）；也如实记录了尚存的打磨点（如复盘槽位提示文案边界、部分网关遥测与开关细节），绝不在汇报材料里粉饰太平。
  • 收紧所有容易“自嗨夸大”的措辞：明确把“100%「KCoder + 白泽」”严格界定为 AI 辅助研发工具链的选用范围（游戏运行时仍可离线完成）；去掉未经单次精确压测支撑的“毫秒级回落”等营销词；在文档里如实区分 offline_redteam 硬审查与 --live 在线审稿，如实写清第一案完整可玩、其余卷宗库槽位为后续扩展预留。

事后证明，这种“先对自己下狠手核对证据链”的习惯，比封板前仓促多塞两个半成品功能靠谱得多。

4.3 尘埃落定

12:00 顺利完成四件套打包校验与提交封板。下午开奖揭晓，我们的《不在场证明》拿下了 专项奖 · AI 开发者创想奖（¥1,000）。

五、 散场与回响（11.20 傍晚）：一年时间，从“穿着大人衣服的看客”到“系统操盘手”

傍晚背着电脑走出长沙国际会议中心，广场上正好铺开一片橘粉色的晚霞，「2026 世界计算大会」的蓝旗在风里飘着。

回想去年 12 月写下《黑客松初体验》时，我还是个码龄刚满两个月的大一新生，觉得参加黑客松像“穿着大人的衣服进入了一场成年人的舞会”，99% 的代码靠学长带飞，最后顺了一兜书签抽了件体恤就乐得不行。一年之后再站在赛场，依然离不开 AI 工具链和队友的并肩作战，但至少这一次，我已经能从第一份 CONTRACT.md 开始搭起状态机架构、划定模型能力与确定性引擎的边界、抢修被 Rebase 误删的前端分支，并盯着 120 项自动化回归用例把项目稳稳交到封板线前。

这一趟 24 小时碳硅接力，留给我最实在的三条工程体悟：

  1. 用契约和确定性规则框住大模型的不确定性：LLM 擅长临场表演与语义判断，但状态流转、权限隔离和终局裁决一定要留在代码引擎里；越早写清 CONTRACT.md，AI 协同时的返工成本越低。
  2. AI 杠杆放大的是工程素养，而不是偷懒的借口：没有 test_http_verify.py、没有脱敏扫描、没有 --verify-baize 对 live/fallback 的严格区分，夜间跑得越快，翻车越惨烈。
  3. 交付前的诚实自审比华丽的 PPT 词藻更有分量：敢把已知限制和验证边界写明白的工程交付件，才经得起任何现场追问。

接下来我们还会继续完善《不在场证明》的后续规划——包括非对称联机玩法（让玩家分别扮演审讯官与嫌疑人在线博弈）以及自定义剧本导入。目前项目代码正在与队友一起做公开前整理与脱敏收尾，待仓库转为公开后，我也会第一时间在这里补上 GitHub 地址。
